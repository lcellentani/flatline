## 1. Problem

Roguelikes deliver the "you can try anything" fantasy in one of two ways: hand-authoring every interaction (NetHack's emergent interaction matrix) or composing a handful of orthogonal physics-like systems (Brogue). Both cap out at what a designer can pre-enumerate or reduce to clean rules, and neither can resolve open-ended *semantic* intent — persuasion, bluffing, improvised use of objects ("burn the door with the oil flask"). We want to test whether a small embedded LLM, acting as a game master, can resolve free-form player intent into legal game-state changes. But we have no defined **contract** for how the GM proposes changes and how the engine contains them — and without that contract we can run neither the "is it fun" test nor the later "can the model do it" test.

(Vision, novelty against what already ships, and the platform/model bets behind this are in the context doc; this spec assumes them.)

**Scope of "v0".** Throughout this document, *v0* names the smallest prototype that tests whether the adjudication mechanic is fun: a **single room**, the GM role played by a **human or a coded stub** (Experiment 1, §4), with **no embedded model** and **no procedural generation**. Every goal and non-goal below is scoped to that milestone; anything past it (the real model harness, memory, multiple rooms, movement) is explicitly deferred.

## 2. Goals

- A single-room scenario (a locked door; a bribable guard holding the key) is playable end-to-end with a **human executing the GM role** against this contract alone — no model, no runtime. The only engine-computed terminal condition in v0 is `player.vital == Dead` (§5); the non-death path (e.g. unlocking `door_north` and leaving) ends the session narratively, at the human GM's discretion, not via a tracked exit/session-over state — that requires the movement system explicitly deferred in §3, and is not itself a v0 goal.
- Every player intent resolves to **either** a set of legal state-deltas drawn from a closed effect vocabulary **or** an explicit `deny`, always accompanied by GM narration. (`partial` also lands in the state-deltas case — it authors a scoped subset of effects, not a third outcome shape.)
- The engine's state can **never** be driven into an illegal configuration by any GM ruling: the validator rejects effects referencing nonexistent ids and effects whose preconditions are unmet; out-of-bounds *magnitudes* are rejected for `damage` (capped to `via`'s table entry) and `modify_disposition` (clamped to the enum range) — `modify_resource`'s `hp`/`gold` deltas are instead constrained at apply time (hp floor/ceiling clamp; a negative-`gold` delta is rejected, not clamped, per §4/§5), a different mechanism than the gauntlet's per-effect magnitude stage, not an additional instance of it.
- Randomized outcomes are owned by the **seeded engine**, with the GM contributing only modifiers — verifiable by replaying a logged run from its event log and obtaining an identical result.
- The same contract is executable by a **human now**; its closed effect vocabulary and validator are designed so it is translatable to a **grammar + validator for Gemma 4 E4B later** (the dual-reader property) — asserted here by construction, not itself checked until Experiment 2's harness exists to validate it.

## 3. Non-Goals

- **Semantic memory / persistent world reactions** — deferred. Adjudication and memory form a stack (memory is an input to the adjudicator), but memory's failures *compound* across turns and bite hardest exactly where the small-model ceiling is weakest; it is also untestable in a single static room. The `set_flag` primitive reserves the hook so memory bolts on later without reworking the contract.
- **The LLM runtime, grammar-constrained decoding, inference harness** — belongs to Experiment 2 (see §4). Conflating it with the fun test poisons the result.
- **Procedural maze / multi-room generation** — adds nothing to an adjudication test; one room exercises the full loop.
- **BG3-style free real-time movement** — the long-term target is a two-clock hybrid (free exploration + turn-based adjudicated interaction; see context doc), but for v0 it is pure engine overhead that tests nothing about the adjudicator and forfeits the latency-hiding trick.
- **A final, exhaustive effect vocabulary** — v0 locks a *representative* 6-primitive starter set (see §4); completeness is not a v0 goal. Additions are driven by intents that Experiment 1 shows map onto no existing combination.
- **Combat balance, progression, art** — irrelevant to whether the core mechanic is fun.

## 4. Design

**Core inversion:** the validator is the actual rules engine; the GM (human stand-in now, LLM later) is a *translator* from open player intent into a closed vocabulary of effects the engine already knows how to apply. The game's rules live in the validator's acceptance logic, never in the prompt. The GM never mutates the world — it fills out a work order in a language the engine defined, and the engine decides whether to honor it.

### Validation Approach (Experiments 1 & 2)

Two orthogonal questions, run in order:

- **Experiment 1 — "Is it fun?"** A human plays the GM behind the validator (Wizard of Oz). Tests the experience; needs no inference. **A coded prototype in which a human still supplies the rulings is still Experiment 1** — it fakes the oracle, not the infrastructure.
- **Experiment 2 — "Can E4B do it?"** Build the real harness; the question becomes a measurable benchmark (schema-valid rate, hallucinated-id rate, re-prompt frequency).

**Kill-switch:** if it isn't fun with a fluent human behind the curtain, a 4B won't save it — so Experiment 1 gates Experiment 2. (Rationale and the model-floor risk that makes Experiment 2 non-trivial are in the context doc.)

### Key Decisions

- **Validator is authority; GM only proposes** — the engine owns all truth and applies only validated deltas. *Alt rejected:* the LLM mutating state directly (ungovernable, untestable, hallucination-prone).
- **Closed effect vocabulary; novel actions map onto existing primitives** *(LOCKED)* — the GM expresses every intent as a combination of a small finite primitive set; "burn the oak door" becomes `set_object_state(door, locked, false)` + narration, not a new `burn` verb. Destruction is `transfer_item(item, holder, <void sink>)`, not a new `destroy` verb. *Alts rejected:* deny-unknown (the NetHack blank cell — defeats the purpose) and add-a-primitive-per-case (infinite chase). Design energy goes into a vocabulary small enough to validate yet expressive enough that most intents land on *some* combination.
- **Effect vocabulary locked for v0 as a 6-primitive starter set** *(LOCKED)* — `damage`, `modify_disposition`, `transfer_item`, `modify_resource`, `set_object_state`, `set_flag` (enumerated below). Representative, not exhaustive (§3); realized in the C++ artifact as a closed `variant`. (`narrate` was dropped — see §5, "`narrate` vs. turn-level narration.")
- **Engine owns the dice** *(LOCKED)* — the GM proposes *modifiers* and the seeded engine performs the roll. Worked: on "I bribe the guard with 15 gold," the GM emits modifiers (`bribable +2`, `generous offer on a 15-gold purse +3`); the engine rolls against them. *Alt rejected:* the model deciding success (inconsistent, gameable, breaks replay determinism). The d20 stays a real d20.
- **`ruling` is a scope decision, not the roll's outcome** *(LOCKED)* — `ruling` (allow/partial/deny) is fixed by the GM at interpretation time: *of what the player asked for, how much is even on the table.* It is independent of any dice. "Bribe the guard to open the door **and** abandon his post" → `partial`, because "abandon post" is refused outright — no roll will ever grant it. The roll only decides success/failure on whatever `ruling` left in play. *Alt rejected:* letting roll margin retroactively influence scope (e.g. a high enough roll widening a `partial` toward `allow`) — rejected because it would blur "what's on the table" (a GM authorship question, decided once, up front) with "did it work" (an engine question, decided by the die), reopening exactly the GM-decides-outcomes failure shape "engine owns the dice" already rules out. Also rejected: folding `ruling` and success into one combined field — rejected because a `deny` and a rolled failure are narratively and mechanically distinct (a `deny`'d action was never on the table at all; a failed roll was on the table and didn't land), and collapsing them would lose that distinction in the logged record.
- **One call authors both outcome branches** *(LOCKED — closes former open question)* — the GM emits, in a single call, the `modifiers` plus a success branch and a failure branch (effects + narration each). The seeded engine rolls once (only if `modifiers` is non-empty) and applies the selected branch. *Alt rejected:* two calls (emit modifiers, then author effects after seeing the roll). Two-call halves per-call schema size but doubles inference round-trips per turn, multiplying exposure to the E4B structured-output floor and working against the turn-based latency-hiding bet (context doc §5–6). Authoring an unused branch is cheap waste; a re-prompted turn is not. Two-call (and roll *margin*) can be layered on later without touching the vocabulary — not a one-way door.
- **`damage` names its weapon explicitly** *(LOCKED)* — every `damage` effect carries a required `via` field (the specific item, or the reserved `UNARMED_ITEM` sentinel) naming what dealt the blow. The validator clamps `amount` to `via`'s entry in a closed damage-cap table, not to "whatever the source is holding" — the GM states the instrument instead of the validator guessing "best weapon held." *Alt rejected:* inferring the cap from the source's inventory (ambiguous once an entity holds more than one item, and silently permits an unscoped "unarmed" default to sneak through undeclared). Every item that can exist in a room's state gets a table row — including ones whose narrative purpose isn't combat (a key to the face still hurts) — consistent with the closed-vocabulary stance already locked for effects, applied one level down to weapons.
- **Environmental hazards get their own `via` sentinel, not a generic one** *(LOCKED)* — `damage` recognizes a small closed set of non-item sentinels alongside real item ids: `UNARMED_ITEM` (fists) and, for the guardroom, `FIRE_ITEM` (shoved into open flame, cap 14 — tuned so a single hit lands `guard_01`, hp 12/12, on `Unconscious` rather than `Dead`; see `gm_rules.hpp`). *Alt rejected:* one generic `ENVIRONMENT_ITEM` sentinel covering every non-item cause — rejected because different hazards plausibly need different caps (fire vs. a collapsing shelf vs. falling), and a single shared cap would either be too weak for the deadliest hazard or too strong for the mildest; a per-hazard sentinel keeps the same closed-damage-table discipline already locked for real items. Both sentinels are carved out of the existence check identically (`gm_rules.hpp`'s existence-check note) — they are never real ids and never appear in `World::entities` or a room's item list.
- **`modify_resource(hp)` is for untargeted causes only** *(LOCKED — convention, not gauntlet-enforced)* — traps, potions, and other causes with no acting entity use `modify_resource`; any hp change resulting from one entity acting on another must be authored as `damage`, so it stays subject to the weapon cap above. *Alt rejected:* giving `modify_resource(hp)` its own gauntlet-enforced magnitude table (mirroring `damage`'s per-`via` cap) — rejected for v0 as a knowingly-accepted gap, not an oversight: `res/workorder_lethal-smoke.json` (untargeted smoke damage, `modify_resource(hp, -13)`) is exactly the uncapped case, constrained only by the applier's floor at 0, not by any pre-apply magnitude check. Closing it would mean either a magnitude table keyed on a `cause`/`source` field `modify_resource` doesn't currently carry, or folding hazards like smoke into `damage` behind a sentinel the way `FIRE_ITEM` already models direct hazard contact — deferred because Experiment 1 (a human GM self-regulating magnitude) doesn't yet need it enforced; revisit if Experiment 2 needs it as a mechanical check. The validator cannot detect a GM routing an attack through `modify_resource` instead — this is an authoring rule for whoever fills out work orders, not a mechanical check.
- **Structured work-order output** — the GM emits the work order below; before anything is applied, its `modifiers` pass a per-turn budget check, the roll selects a branch, and every effect in that branch is validated through a fixed gauntlet.
- **Gauntlet validates only the roll-selected branch; fails fast per effect** *(LOCKED)* — the roll (or its absence) picks a branch first; the gauntlet only ever runs against that one `vector<Effect>`. On the first effect that fails any stage, the whole batch is rejected and evaluation stops — no partial application, consistent with "apply atomically." *Alt rejected:* validating both branches always, and/or collecting every violation instead of the first — more accurate for Experiment 2's failure-rate metrics, but pure overhead for Experiment 1, where a human GM already knows both branches are sane. Revisit once Experiment 2 tooling exists.
- **Preconditions fold forward across a batch; same-batch conflicts get their own stage** *(LOCKED — closes "Same-batch effect conflicts")* — the preconditions stage now checks each effect against the state this branch's own prior effects have already produced, not a single static pre-turn snapshot; the whole batch still rejects atomically on the first failure, exactly as above, and `apply()` is untouched — this changes how legality is *checked*, not how the batch is *applied*. A precondition broken specifically by an earlier effect in the same batch (two `transfer_item`s claiming one item; two `modify_resource(gold)` spends that individually fit the balance but not together) is reported as its own `Stage::BatchConflict`, distinct from an ordinary precondition that was never legal even at turn start, and names the earlier effect responsible (`conflicting_with_index`) so a re-authored work order doesn't have to guess which effect to fix. `referenced ids exist` deliberately stays checked against the untouched pre-turn snapshot — an item consumed earlier in the batch and referenced again is a same-batch conflict, not a hallucination. *Alts rejected:* a dedicated batch-level pre-check scanning for same-resource claims before anything runs (cheaper, but doesn't generalize — misses `modify_disposition` compounding incorrectly at its enum ceiling, a real bug of the same shape, caught only because the general mechanism covers it for free); authoring-convention-only (prior art already rejected this for `modify_resource(hp)` below — invisible in Experiment 1, meaningless in Experiment 2); a `NeedsResolution` outcome with interactive mid-turn resolution (reopens the one-call decision above — a resolve step is a second inference dependency, not free for Experiment 2 even where it's free for a human GM).
- **Applier is a pure function; `World` gains a `flags` field** *(LOCKED)* — `apply(world, effects)` (`gm_applier.hpp`) returns a NEW `World` rather than mutating the one passed in, matching `run_gauntlet`'s own shape (`const World&` in, a new value out) rather than introducing an in-place-mutation style found nowhere else in the codebase. It takes a gauntlet-approved batch as a precondition; it performs no validation itself and cannot fail. `set_flag` previously had no field to write into anywhere in `World` — `flags: map<string, PropertyValue>` closes that gap immediately, consistent with "deferred gaps must be named, not silently ignored" (the same shape as `Damage.via`'s fix): a vocabulary member that writes into the void at apply time is a silent bypass waiting to happen.
- **hp floor is uniform across `damage` and `modify_resource(hp)`** *(LOCKED)* — the applier clamps the resulting hp to `>= 0` regardless of which effect produced the delta. Considered scoping the floor to `damage` only (the spec's original wording only ever mentioned damage's floor) — rejected: the floor is a property of hp itself, not of which effect touched it, so a trap's untargeted `modify_resource(hp)` delta is floored exactly like a sword's `damage`. Gold gets no equivalent applier-side floor — `gold_spend_legal` already rejects (not clamps) any delta that would go negative at the gauntlet stage, so a negative-gold batch never reaches the applier in the first place; hp needed a *clamp* instead of a *rejection* because, unlike overspending gold, dealing lethal damage has to be a legal outcome.
- **hp ceiling (`max_hp`), symmetric with the floor; vital state as a third axis of entity state** *(LOCKED)* — `Entity`/`Player` gain `max_hp` (seeded at their current, full-health values: `guard_01 = 12`, `player = 20`) and `VitalState { Alive, Unconscious, Dead }`. A flat enum, not a `std::variant` — considered and rejected for v0, since nothing needs per-state payload yet and the two give identical transition-legality safety; revisit only once a concrete consumer (e.g. overkill-magnitude narration) actually needs one. `Dead` is a terminal, engine-derived state (never GM-proposed — there is no `set_vital_state` effect), computed from a turn's *batch-level* raw hp overshoot against a `kDeathOvershoot = -5` threshold, not per-effect — the per-effect floor/ceiling would otherwise erase the signal before a second effect in the same turn could see it. Full rationale, transition table, and precondition changes: §5, "hp ceiling and alive/dead state."
- **Roll scheme: d20 + modifier sum vs. a fixed DC** *(LOCKED)* — concretizes "engine owns the dice" above. The seeded engine draws 1d20, adds the work order's signed modifier sum, and compares the total to a fixed, engine-owned `kDifficultyClass = 15`; success iff `total >= kDifficultyClass`. *Alt rejected:* a modifier-sum → probability-curve draw — its main structural edge (bounding outcomes for free, however large the modifiers get) is subsumed by the modifier budget below, and it costs the "sum +5 needs a 10+" legibility a human GM reads at the table without running code. Also rejected: summing multiple d20s to widen the numeric range — trades a flat, uniform distribution for a triangular one, so a modifier point buys less swing near the middle and more at the tails, reintroducing the same legibility cost. The DC is a single fixed constant, not authored per-work-order — letting the GM set its own target would let it guarantee an outcome without ever touching the die, the same failure shape "engine owns the dice" already rules out, just relocated from the die to the goalpost. (A `DifficultyTier` enum mapped through a closed table is the parked extension point if a second room needs variable difficulty — not built for v0.)
- **Modifier budget: `kModifierBudget = 5`, derived from the DC, gauntlet-enforced** *(LOCKED)* — a work order's `modifiers` must sum to a *magnitude* (Σ|value|, not net sum — a net-only cap would still let a GM stack unbounded negative modifiers to force a guaranteed failure without ever tripping a positive-side limit) of at most 5, checked by a gauntlet stage that runs against the whole work order *before* the roll — enforced, not an authoring convention, since unenforced is invisible in Experiment 1 (a human self-regulates) but meaningless in Experiment 2 (nothing stops a model from ignoring unenforced prose). 5 is not an independent tuning choice: at DC 15 on a single d20, it is the largest budget that keeps both roll directions strictly probabilistic (best case needs a 10+, 55%; worst case needs a 20, 5%) — one point higher and the best case would need less than 1, silently reopening "the GM guarantees the outcome" at the modifier-sum level instead of a single field. Spend is `<=`, not exact — a GM with one honestly-justified modifier shouldn't be forced to invent a second one just to max out the pool.
- **Replay seed: `FNV-1a-64(turn_number, full work-order JSON dump)`** *(LOCKED)* — not `std::hash`, which is unspecified across compilers and standard-library versions and would silently break the one property this scheme exists for: replaying a logged run identically later, possibly on a different machine. `turn_number` is deliberately **not** a field on the work order — it is tracked by the caller (engine/harness, eventually the logger), keeping the contract scoped to one turn at a time. Hashing the work order's full canonical dump (prose included, not a curated mechanical-fields-only subset) is a real behavioral consequence, not a technicality: two GMs describing the identical bribe with different wording roll differently. The roll result carries `die`, `modifier_sum`, and `total` alongside `success`, not just the bool — a replay log needs to show its work.
- **Replay log: one entry per turn, self-contained, JSON Lines** *(LOCKED)* — each turn appends exactly one entry to an append-only JSON Lines file, regardless of which of three outcomes it reached (modifier-budget rejection, gauntlet rejection, applied) — the gauntlet's internal per-effect stages never get their own line; one work-order call is one turn is one entry, mirroring the already-locked one-call-per-turn architecture. An applied entry carries both the pre-turn and post-turn `World` in full, not deltas folded forward from a genesis snapshot, so any single logged turn is independently replayable and verifiable without first replaying every turn before it. Named cost, accepted rather than hidden: every world state is this way stored twice (a turn's post-state equals the next turn's pre-state); immaterial at this room's size, revisit if session length ever makes storage hurt. *Alt rejected:* replaying strictly from turn 0 by folding each turn's effects forward (cheaper storage, but a single turn is no longer independently verifiable), and a genesis-snapshot-plus-checksum hybrid (parked as the fallback if storage cost becomes real). The three outcomes are a closed set with mutually exclusive fields, not one flat struct with "present only if" fields — a rejected-before-the-roll turn structurally cannot carry a roll result to be misread, and a rejected-before-apply turn structurally cannot carry a post-turn `World`.

### The Acceptance Gauntlet (ordered)

Two tiers, run in order; a turn ends at whichever of three exit points it reaches, and exactly one log entry is appended regardless of which.

**Per turn**, against the work order as a whole, before any branch is selected: **modifier budget** (Σ|value| across `modifiers` ≤ `kModifierBudget`) — a work order that exceeds it is rejected and logged here, before the roll ever runs, so an unbounded modifier list can never force the roll's outcome. Otherwise, **roll**: no roll if `modifiers` is empty (success automatic); otherwise d20 + modifier sum vs. `kDifficultyClass` picks `effects_on_success` or `effects_on_failure`.

**Per effect**, on the roll-selected branch: **schema-valid** is discharged upstream, at JSON parse, across every effect in *both* branches — a well-formed `Effect` cannot fail this by the time the gauntlet sees it. The remaining stages run only on the selected branch: **referenced ids exist** in current state (the hallucination check, always against the untouched pre-turn snapshot — with an explicit carve-out for the `VOID_ENTITY`/`UNARMED_ITEM` sentinels, which are never real ids) → **preconditions met**, checked against the state this branch's own prior effects have already folded in, not a single static snapshot (the guard can't hand over a key he isn't holding; `modify_resource(gold)` can't take the actor negative; a precondition broken specifically by an earlier effect in this same batch reports as its own **batch conflict**, naming that earlier effect, rather than as an ordinary precondition failure) → **magnitude in bounds** (clamp `damage` to `via`'s cap in the closed damage table; `modify_disposition`'s clamp also reads the folded state, so a batch's own effects compound correctly at the enum ceiling instead of each clamping from the same starting value). The first effect to fail any of these is rejected and logged here, at that effect and stage.

Once every effect in the branch survives: **apply atomically** against the real pre-turn `World` in one pass — the preconditions stage's forward-folding above is internal to validation only, discarded once the branch survives; `apply()` never sees it and needs no batch-internal state of its own — then **log** — one self-contained entry either way: the raw work order and the roll's seed/result (if any) on every outcome, plus the applied deltas and both world snapshots on this one.

### Contract Schemas

These are language-neutral; the C++ artifacts (`gm_effects.hpp` for the vocabulary and work order, `gm_state.hpp` for the state model, `gm_rules.hpp` for the validator's reference tables — including the roll scheme's constants — `gm_json.hpp` for the JSON ↔ struct serialization bridge, `gm_log.hpp` for the replay log's entry/outcome schema) realize them as types, lookups, and parse/dump functions. `gm_gauntlet.hpp`, `gm_applier.hpp`, and `gm_roll.hpp` are control flow over these schemas, not schemas themselves, and are deliberately not listed here.

**Engine-owned state (the source of truth).** Conceptual shape:

```
room    : { id, exits: { <dir>: { object } } }
objects : [ { id, <properties…>, e.g. locked, material } ]
entities: [ { id, hp, disposition, holds: [item], persona } ]
player  : { id, hp, gold, inventory: [item] }
flags   : { <key>: <bool|int|string> }   // set_flag's write target; dormant memory hook, v0
```

Worked instance for the v0 room: a `guardroom` with a north exit gated by `door_north` (`locked: true`, `material: oak`); a `guard_01` (`hp 12`, `disposition neutral`, `holds [key_north]`, persona "bored, underpaid, bribable"); a `player` (`hp 20`, `gold 15`, `inventory [dagger, oil_flask]`).

**The work order (what the GM emits, once per player turn).**

```
interpretation        : one line — what the player is trying to do
ruling                : allow | partial | deny   // scope decision, fixed at interpretation; NOT the roll result
modifiers             : [ { label, value } ]     // feed the engine's roll; empty ⇒ no roll, success is automatic
effects_on_success    : [ <effect>, … ]          // applied if the roll succeeds (or unconditionally if no roll)
narration_on_success  : 1–2 sentences, GM voice
effects_on_failure    : [ <effect>, … ]          // applied if the roll fails; empty when modifiers is empty
narration_on_failure  : 1–2 sentences, GM voice
```

Because both branches are authored up front and the engine's roll is seeded, the whole turn is replayable from the logged work order plus the seed/result — the roll picks a branch, it does not author one. A `deny` ruling is expressed as empty effect branches with refusal narration.

**Effect vocabulary (representative v0 — not final).**

```
damage(source, target, via, amount)      // via required: item, UNARMED_ITEM, or a hazard sentinel (e.g. FIRE_ITEM); amount clamped to via's cap in the closed damage table
modify_disposition(entity, delta)        // clamped to the disposition enum range; player is not eligible (no disposition field)
transfer_item(item, from, to)            // to = the void sink ⇒ item is consumed/destroyed
modify_resource(actor, "gold"|"hp", delta)// gold delta rejected (not clamped) if negative; gold is player-only (no `gold` field on Entity) — hp is eligible on both
set_object_state(object, property, value)// property must exist in the object's schema (instance-is-schema: the object's seeded keys)
set_flag(key, value)                     // memory hook — dormant in v0
```

### Worked Examples

- **Bribe (partial scope, with a roll).** Intent "bribe the guard with 15 gold for the key." `ruling = partial` — "hand over the key" is on the table; "abandon his post" was refused at the scope level, permanently, regardless of the roll. Modifiers `[bribable +2, generous +3]` — magnitude 5, exactly at `kModifierBudget`; the engine rolls 1d20 + 5 against `kDifficultyClass = 15` (a 10 or better succeeds). **On success:** `modify_resource(player, gold, -15)`, `transfer_item(key_north, guard_01, player)`, `modify_disposition(guard_01, +1)`; narration: he pockets the coin and slides the key over, but won't budge from his post. **On failure:** `modify_disposition(guard_01, -1)`; narration: he shoves the coin back, insulted.
- **Burn the door (novel → primitives, no roll).** Intent "pour the oil flask on the door and light it." `ruling = allow`, `modifiers` empty ⇒ no roll, success is unconditional. Effects: `set_object_state(door_north, locked, false)` + `transfer_item(oil_flask, player, <void>)`; narration covers the burn-through. No failure branch. The novel verb is expressed in existing levers.
- **Hallucination (deny at the gauntlet).** GM proposes `transfer_item(silver_key, guard_01, player)` but no `silver_key` exists in state. The work order is *schema-valid*; the rejection happens one stage later at the existence check. Demonstrates that the validator, not the GM, is the backstop.
- **Over-budget modifiers (rejected before the roll).** GM proposes `[bribable +2, generous +3, desperate +3]` (magnitude 8) for the bribe. The modifier-budget stage rejects it before any roll runs — 8 exceeds `kModifierBudget = 5` — so the turn never reaches the gauntlet or the applier. The work order must be re-authored with modifiers back under budget; nothing in state changes. Demonstrates the per-turn tier of the Acceptance Gauntlet, distinct from the per-effect tier the other three examples exercise.
- **Same-batch conflict (rejected at apply-time, diagnostic names the culprit).** GM proposes `transfer_item(key_north, guard_01, player)` *and* `transfer_item(key_north, guard_01, <void>)` in the same `effects_on_success` — the key handed to the player and destroyed, in one batch. Both effects independently pass against the untouched pre-turn snapshot (`guard_01` really does hold `key_north` at turn start); folded forward, the second effect sees the first already moved it. Rejected at effect 1, `Stage::BatchConflict`, `conflicting_with_index = 0` — distinct from a hallucination or an ordinary precondition failure, specific enough that the work order can be re-authored (drop one of the two, or reorder them) without guessing which effect was the problem.
- **Push into the flames (hazard `via`, no item involved).** Intent "shove the guard into the fire engulfing the door." `ruling = allow`, modifiers `[fixated on the fire +2, on-edge from the fire -1]` — magnitude 3; the engine rolls 1d20 + 1 (net) against `kDifficultyClass = 15`. **On success:** `damage(player, guard_01, FIRE_ITEM, 14)`; narration: he stiffens, then crumples, unconscious. Fourteen against `guard_01`'s 12 max hp overshoots to `-2`, inside `[-4, 0]` — `Unconscious`, not `Dead`, exactly the tuning `FIRE_ITEM`'s cap was chosen for (§4 Key Decisions). **On failure:** `damage(guard_01, player, UNARMED_ITEM, 1)` + `modify_disposition(guard_01, -1)`; narration: he catches himself and shoves back. Demonstrates a `damage` effect whose `via` is a hazard sentinel rather than a held item — the existence and `holds()` checks carve out `FIRE_ITEM` exactly as they do `UNARMED_ITEM`.

### How It Fits / The Seam It Defines

Greenfield: there is no existing codebase to slot into; this contract *defines the seam* between two halves. On one side, the deterministic engine owns state, the seeded RNG, and (later) movement. On the other, the adjudication layer turns intent into proposed deltas. The validator's acceptance rules are the **shared spine** both experiments depend on — executed identically by a human this week and a model later. The GM (human or model) is a swappable component behind a single boundary; everything upstream of it is unchanged when the model drops in.

## 5. Open Questions

- [x] **Validator reference data** — resolved; realized in `gm_rules.hpp` as hardcoded C++ tables (storage choice locked, matching the "representative, not final" spirit already locked for the effect vocabulary). Locked: (a) precondition rules — `transfer_item` requires `from` to hold `item`; `damage` requires `source` to hold `via` (or `via` = the `UNARMED_ITEM`/`FIRE_ITEM` sentinels, carved out of the existence and `holds()` checks identically — see §4 Key Decisions); `modify_resource(gold)` rejects (not clamps) a delta that would take the actor negative; `transfer_item(from == to)` and self-`damage` are legal no-ops/allowed; (b) `set_object_state` schema is **instance-is-schema** — an object's legal properties are exactly the keys it was seeded with in the room JSON, and the new value's type must also match the existing property's type (a bool-valued property can't be overwritten with a string); revisit once a second room needs per-type schemas; (c) `damage` is capped by a required `via: ItemId` field (not inferred from the source's inventory) against a closed per-item table — every item in the room's state needs an entry, no fallback for a miss; (d) no `modify_resource` resources beyond `gold`/`hp` needed for the v0 room.
- [x] **hp floor** (partially resolves the item below — LOCKED only the following) — `gm_applier.hpp` floors the resulting hp at 0, applied uniformly across BOTH `damage` and `modify_resource(hp)`, not just damage: the floor is a property of hp itself, not of which effect touched it (see Key Decisions). Damaging an already-0-hp target is legal and simply re-clamps to 0 — same no-op precedent already established for self-`damage` and `transfer_item(from == to)`.
- [x] **hp ceiling and alive/dead state** — resolved. Reachable in v0 as scoped, not deferrable: `modify_resource(hp, +N)` had no magnitude check at all (a GM could legally grant unbounded hp with no item involved), and the guardroom's own dagger (cap 4) and oil_flask (cap 2) are already enough to drive `guard_01`'s 12 hp to 0 and past it across a handful of turns — the two locked resolutions below close both gaps.

  **(a) hp ceiling — Option A2, locked.** `Entity`/`Player` both gain a `max_hp` field; `gm_applier.hpp`'s `adjust_hp` clamps to `[0, max_hp]`, symmetric with the already-locked floor and applied the same uniform way (both `damage` and `modify_resource(hp)`, per-effect). Seeded values: `guard_01.max_hp = 12`, `player.max_hp = 20` — both entities start at full health in `room_guardroom.json`, so the ceiling equals their current seeded `hp` with nothing invented; revisit only if a second room's healing content gives reason to diverge.

  **(b) alive/dead state — a third axis of entity state**, alongside `disposition` (attitude) and `hp` (a number): what an entity currently *is*. Realized as `enum class VitalState { Alive, Unconscious, Dead }` on both `Entity` and `Player` — a flat enum, not a `std::variant`, since nothing needs per-state payload yet (rejected alternative: the payload-carrying variant, revisit only when a concrete consumer — e.g. the overkill-narration idea below — actually needs one; until then the two give identical transition-legality safety at a fraction of the machinery). Known limit of the flat-enum choice, stated rather than left to be discovered later: cheap to add more *mutually exclusive* states, cannot represent states *co-occurring* (e.g. poisoned *and* unconscious) without a structural change.

  Transition table (`gm_rules.hpp::derive_vital_state`, a pure function — vital state is never GM-proposed, there is no `set_vital_state` effect, so this is engine-internal math, not a gauntlet precondition):
  - `Alive → Unconscious` — batch overshoot in `[-4, 0]`
  - `Alive → Dead` — batch overshoot `≤ kDeathOvershoot = -5`, direct (a big enough blow skips `Unconscious` entirely)
  - `Unconscious → Dead` — same `-5` threshold finishes off an already-downed target
  - `Unconscious → Alive` — any `modify_resource(hp, +)` that clears 0; no separate threshold
  - `Dead → ` — terminal for v0. Recoverable only by a future item/magic feature that doesn't exist yet; the missing exit edge is a named decision, not an oversight, and costs only a new transition-table row to add later (enum arms are additive, same as `narrate`'s removal cost the other direction).

  `kDeathOvershoot = -5` is batch-level, not per-effect: the per-effect hp floor already erases the overshoot signal by the time a second effect in the same turn would need it, so `gm_rules.hpp::vital_deltas` sums a turn's raw (pre-floor, pre-ceiling) hp deltas per target before comparing against the threshold — reused identically by the applier (to derive the stored state) and the log (for the overkill field below), so the two can't drift apart. With the room's current weapon caps (dagger 4, oil_flask 2), no single item can ever reach `-5` alone — only combining damage effects in one work order, or a repeated finishing blow, crosses it. Deliberately hard to reach by accident, easy to reach on purpose.

  Preconditions (`gm_gauntlet.hpp`, new predicates in `gm_rules.hpp`): `modify_disposition` now requires the target to be `Alive` (rejects both `Unconscious` and `Dead` — an entity that isn't fully conscious has no attitude to modify). Any hp-affecting effect (`damage` or `modify_resource(hp)`) targeting a `Dead` entity is rejected — `Dead` is terminal either direction, damage or heal. `transfer_item` gets **no new gate** — deliberately locked as unchanged: looting or inspecting an `Unconscious` or `Dead` entity was already legal (its only precondition was ever `holds()`) and stays that way.

  Player gets the identical three-state set. Reaching `Dead` ends the session — `gm_rules.hpp::session_over(world)` is the rule (`player.vital == Dead`), proven correct in `test_applier.cpp`, but **not yet wired to a turn loop**: `wizard_of_oz_demo.cpp` runs one hardcoded turn, not a real multi-turn loop — building that loop is separately named, on the horizon. The loop's own future change is wiring this predicate in, not new logic.

  **Overkill magnitude** (the idea flagged in this entry previously): resolved in favor of storing it explicitly, not reconstructing it on demand. Building the vital-state derivation above already requires computing the batch's raw pre-floor total to decide `Dead` vs. `Unconscious` in the first place — capturing that number costs nothing additional at the exact point it's already computed, whereas leaving it "reconstructable" would require a future consumer to re-derive it via a dedicated replay pass. `gm_applier.hpp::vital_transitions(world_before, effects)` returns one entry per entity whose vital state changed this turn (empty on ordinary turns), each carrying `overkill` — the raw total when it lands on `Dead`, `0` for an `Unconscious` transition. `gm_log.hpp`'s `Applied` outcome carries this as `vital_transitions`, populated by the caller (not derived inside `apply()`, which keeps its existing `World`-in/`World`-out signature untouched for every existing call site) — present as `[]` on non-combat turns, not omitted (unlike `roll`, which genuinely is absent on a no-roll turn).
- [x] **Same-batch effect conflicts** — resolved. The preconditions stage now folds state forward across a branch instead of checking every effect against a single pre-turn snapshot, so two effects in the same batch that would each independently look legal against an untouched snapshot now see each other: `transfer_item.from` no longer holds an item a prior effect in the same batch already moved; `modify_resource(gold)` sees the balance a prior spend in the same batch already reduced. A failure caused specifically by an earlier effect in the same batch is reported as its own `Stage::BatchConflict` (not folded into an ordinary `Preconditions` failure), naming the earlier effect responsible via `Failure::conflicting_with_index` — a precondition that was never legal even at turn start is a different failure with a different resubmission fix, and the two must not share a label, the same discipline session log 4 §2.1 already applied to a table gap vs. a hallucination. `referenced ids exist` deliberately stays checked against the untouched pre-turn snapshot, not the folded state: `item_exists` proves an id is real *somewhere in current holder state*, so an item a prior effect already consumed to the void sink would otherwise misreport as a hallucination instead of the same-batch conflict it actually is. `modify_disposition`'s clamp also now reads the folded state — a bonus fix inside the same mechanism, not a separately-traced bug: two disposition shifts on the same entity in one batch now compound correctly at the `[Hostile, Allied]` ceiling instead of both clamping from the same pre-turn starting value and silently overshooting it once applied. Still whole-batch rejection, still no partial application — folding is internal to validation only; `apply()` is unchanged and still applies the gauntlet-approved batch in one atomic pass against the real pre-turn `World`. *Alts rejected:* a dedicated batch-level pre-check scanning for same-resource claims before anything runs (doesn't generalize — misses the disposition-ceiling case above); authoring-convention-only (prior art already rejected this for `modify_resource(hp)` above — invisible in Experiment 1, meaningless in Experiment 2); a `NeedsResolution` outcome with interactive mid-turn resolution (reopens the one-call decision — a resolve step is a second inference dependency Experiment 2 doesn't get for free just because a human GM does).
- [x] **`narrate` vs. turn-level narration** — resolved; `narrate` removed from the effect vocabulary (now 6 primitives). It was fully inert (`apply_one` no-op, both gauntlet stages trivially pass) and unused by all four locked worked examples; every gameplay case tried collapses into `narration_on_success`/`narration_on_failure`. The one surviving argument for keeping it — per-effect attribution for a future memory/log consumer — is speculative, not a committed roadmap item the way `set_flag`'s memory hook is, so it doesn't meet the bar for a dormant reservation. Re-add only if that need becomes committed; as a `variant` arm the re-add is additive, not a rework. The human GM now has one unambiguous narration channel.
- [x] **Failure policy** (Experiment 2) — **relocated, not resolved here.** On malformed or illegal model output (re-prompt / fall back to `deny` / clamp) is a real design question, but it's a question about an inference harness that doesn't exist yet — answering it now means guessing, not deciding. Moves out of this document entirely, to be scoped via `/spec-new` (interview-first, not fabricated here) once Experiment 2 harness work actually starts. No longer counted as an open point against this spec's Ready status.
- [x] **Trigger boundary** (deferred) — **relocated, not resolved here.** Once movement exists, what crisp condition flips a free deterministic action into an adjudicated one — moot for v0's single static room, and premature to answer before a movement system exists to define the boundary against. Moves out of this document, to be scoped via `/spec-new` once movement work starts. No longer counted as an open point against this spec's Ready status.
- [x] **Unvalidated branch hides Experiment 2 failures** (surfaced while locking gauntlet control flow) — **relocated, not resolved here.** The gauntlet only validates the branch the roll selects (or the success branch when there's no roll); the other branch is never checked. A hallucinated id or an out-of-bounds magnitude sitting in the branch that never fires won't count toward schema-valid rate or hallucinated-id rate — harmless for gameplay (an unfired branch never applies) but understates Experiment 2's numbers if measured naively. Genuinely a benchmark-harness design question, not a v0 engine one — no benchmark harness exists yet to be wrong about. Moves out of this document, to be scoped via `/spec-new` alongside the failure-policy question above once Experiment 2 tooling exists — likely the same future spec, since both presuppose the same not-yet-built harness; may end up split from the trigger-boundary question above if that turns out to be movement-scoped rather than Experiment-2-scoped. Not decided yet — the point of relocating now is to stop these three from blocking this document, not to prematurely fix their eventual home.
