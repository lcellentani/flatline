## 1. Problem

Once a session ends (`session_over` true) — or a GM simply wants to restart mid-session — `woz_gui` has no in-app way to begin a fresh one. `world`, `turn_number`, `log_entries`, and `session_over` are all plain `main()`-local state with no reset path, and `docs/specs/woz-gui-qol.md` §4 explicitly named this gap ("absent any in-app way to start a new session today") when it decided Reset/Save should stay usable after session-over rather than freeze the whole editor. The only way to actually play again today is killing and relaunching the whole `woz_gui.exe` process — a full SDL/OpenGL/ImGui bootstrap just to re-run `parse_world` on the same room file.

## 2. Goals

- A "New Session" button, clickable at any time — not gated by `session_over`, unlike Submit — immediately resets all in-memory session state in one click, no confirmation step: `world` reloaded fresh from the same room file the app was launched with, `turn_number` back to `1`, `session_over` cleared, `log_entries` emptied. Verifiable by: clicking it while the session-over banner is showing clears the banner and re-enables Submit; clicking it mid-session immediately replaces the displayed World/turn counter; in both cases the Log panel's entry list and the WorkOrder panel's This Session group are both empty immediately after.
- The editable WorkOrder buffer, the Save filename field, any stale selection into the now-emptied `log_entries`, its preview text, and any previously-shown parse error are all reset alongside the session state — no leftover draft, filename, dangling selection, stale preview, or unrelated old error banner survives into the new session. Verifiable by: typing a draft, entering a Save filename, selecting a This-Session entry, and triggering an unrelated parse error, then clicking New Session, leaves the editor blank, the filename field empty, nothing selected and no preview text in the WorkOrder panel's This Session group, and no error banner showing.
- Each session — including the very first one at process startup, not only ones started via this button — writes to its own dedicated, uniquely-named log file, so no two sessions in the same `woz_gui` run (or across separate runs) ever both contain a `turn_number: 1` entry in the same file. Verifiable by: clicking New Session twice in one run produces two distinct files under the existing generated-log convention, each independently replayable from turn 1 with `gm_log.hpp`'s existing replay check.
- The Saved group (`workorders/*.json`) — contents and current selection/preview alike — is completely unaffected by New Session; it's an on-disk template library, not session state. Verifiable by: with a Saved entry selected and previewed, clicking New Session leaves that selection and preview exactly as they were.
- If reloading the room file fails (e.g. it was edited into invalid JSON on disk since launch), New Session refuses and shows an inline error directly in the Room Description panel — styled identically to `parse_error`'s existing red text treatment, but its own separate state, since `parse_error` itself is owned and rendered by the WorkOrder panel, a different window — leaving the current session completely untouched. Verifiable by: hand-corrupting the room file on disk, then clicking New Session, shows an inline error in the Room Description panel and leaves `world`/`turn_number`/`log_entries` exactly as they were before the click.

## 3. Non-Goals

- **Picking a different room file** — New Session only ever re-parses the same `room_path` the app was launched with (`argv[1]` or the `room_guardroom.json` default); switching rooms mid-app would need a file-picker widget and is a meaningfully bigger feature, left for a future spec if it's ever wanted.
- **A confirmation modal before wiping the session** — matches `docs/specs/woz-gui-qol.md`'s locked "no confirm-modal popup pattern" decision; New Session stays a single, immediate click like Reset.
- **Archiving, rotating out, or cleaning up old session log files** — each session's log file is written and then left alone, same as `gui_layout.json`/`gui_session_log.jsonl` already accumulate untouched in `build/bin/` today; managing old files is a filesystem concern outside the app.
- **Any change to `process_turn`/gauntlet/applier/roll semantics** — New Session only resets which `World`/`turn_number`/log file a turn gets processed against; the processing itself is unchanged.
- **Any new cross-relaunch persistence** — New Session does at runtime, without the process-bootstrap cost, what a full relaunch already does today; it doesn't introduce any new "remembered across restarts" state (that's what `gui_layout.json` is for, unaffected by this spec).
- **`woz` or `woz_loop`** — this spec, like `woz-gui-qol.md`, touches only `src/woz_gui.cpp`; the other two front ends are unaffected.

## 4. Design

### Key Decisions

- **New Session resets *all* in-memory session state in one shot — `world`, `turn_number`, `session_over`, `log_entries`, `selected_entry`, `selected_session_turn`, the editable `wo_text`/`wo_text_buf`, `save_filename`/`save_filename_buf`, and (on a successful reset) `parse_error`** — rather than a narrower reset (e.g. just `world`/`turn_number`). A partial reset would leave indices (`selected_entry`, `selected_session_turn`) pointing at a now-empty `log_entries`, a stale draft/filename carried into a session it was never written for, or a leftover error banner from some earlier, unrelated Submit/Save failure. (`wo_preview_text`'s own reset is conditional, not unconditional — see the next bullet.) Rejected: leaving the editable buffer/filename untouched on the theory a GM might want to carry a draft into the new session — undercuts the button's own purpose (start clean), and Reset already exists for anyone who wants to keep editing without resetting the session.
- **`wo_preview_text` and the Saved group's own selection (`selected_saved_file`) are cleared only when the stale selection being wiped was specifically a This-Session one — not unconditionally, and not when a Saved entry was selected instead.** `wo_preview_text` is one shared variable populated by whichever of the two mutually-exclusive selections (`selected_session_turn`, `selected_saved_file`) was last clicked, and it renders unconditionally regardless of which — so it's cleared exactly when `selected_session_turn` was the active one (its content is now stale, since `log_entries` is empty) and left alone when `selected_saved_file` was active instead (its content still correctly reflects an on-disk file New Session never touches — previous Non-Goal). `selected_saved_file` itself is never touched by New Session at all. `selected_session_turn`/`selected_entry`, by contrast, always clear since they index `log_entries` directly and that vector is now empty. Since the two selections are already mutually exclusive elsewhere in the file, there's no case where both are live at once.
- **A failed room-file reload leaves the current session completely untouched and surfaces its own inline error, rendered in the Room Description panel next to the button** (same red text styling `parse_error` already uses, but a distinct variable — reusing `parse_error` itself would either show the failure in the wrong window, since it's rendered inside the WorkOrder panel's own `Begin`/`End` block, or risk being silently overwritten by whatever the WorkOrder panel's Submit/Save handlers do to that same variable later in the same frame), rather than partially applying the reset (e.g. clearing `log_entries` before discovering the reload fails) or crashing the process the way the equivalent startup failure does today (`printf` + `return 1`). Matches Submit's and Save's own established "parse/validate before mutating anything" shape — reload the room file into a local first, and only commit it to `world` (and only then clear the rest of the session state) if that succeeds.
- **Every session's log file gets a fresh, uniquely-named path — including the very first session at process startup, not only ones started via New Session** — computed once at startup and recomputed on every New Session click, replacing the single fixed `kGuiLogPath` constant with a per-session generated path. Rejected: keeping the first/startup session on the literal fixed `gui_session_log.jsonl` name and only rotating from the second session onward — backward-compatible with the current literal filename, but introduces a first-session-is-special branch this codebase's own specs consistently avoid (e.g. `woz-gui-qol.md`'s single `load_or_default()` path for "never saved" and "saved but broken"), for no benefit since nothing in the repo depends on the literal filename (confirmed by a repo-wide grep — only descriptive doc mentions, no tooling).
- **The generated filename is a local-time, millisecond-granularity timestamp suffix** (e.g. `gui_session_log-20260718-153042-137.jsonl`), not an in-process counter. Second granularity was the first draft's choice but doesn't actually hold up: a real double-click on the button (~200–500ms apart) can straddle a one-second boundary, and since `gm_log.hpp`'s `append_to_file` opens in append mode, a same-second collision wouldn't error — it would silently interleave both sessions' entries, including two separate `turn_number: 1` lines, into one file (caught in `/spec-review`). Millisecond resolution closes that gap for any realistic human click cadence without adding a counter or a startup scan. Rejected: an in-process counter instead of a finer timestamp — would need to survive relaunches to stay unique across separate runs (requiring a startup scan of existing files, the exact kind of complexity this decision avoids), where a sufficiently fine timestamp is unique across both same-run and cross-run sessions without tracking any extra state. Rejected: also appending a monotonic in-process counter on top of the millisecond timestamp to close the now-astronomically-unlikely remaining collision window — solves a problem that doesn't manifest under any realistic manual GM use; millisecond resolution alone already satisfies "distinct per session" for a human clicking a button.
- **`.gitignore`'s existing exact-match `gui_session_log.jsonl` line becomes a glob, `gui_session_log*.jsonl`** — the exact-match entry only ever covered that one literal filename; once every session (including the first) gets a generated timestamped name, none of them would match it and every session log would show up as untracked. The glob covers every generated name (and the old literal one too, trivially) with a one-line change.
- **New Session is always enabled, with no disabled/"nothing to reset" state**, unlike Reset (which disables when the buffer is already blank). Reset's disabled state communicates something meaningful (nothing staged to lose); New Session doesn't have an equivalent natural condition worth gating on, and the interaction is cheap and non-destructive enough (immediate, no confirmation, per the Non-Goals) that always-clickable is simpler than inventing one.
- **The button lives in the Room Description panel, unconditionally visible** (not only inside the existing `if (session_over)` banner block, since New Session must also work mid-session) — that panel already owns the session-over messaging and has no other action buttons competing for space, unlike the WorkOrder panel's already-packed Submit/Reset/Save/filename row. It also gains one small addition of its own: an inline-error render block for the reload-failure case above — the first error-rendering code this panel has had.

### How It Fits Existing Systems

Touches only `src/woz_gui.cpp` and `.gitignore` — no change to `gm_turn.hpp`, `gm_log.hpp`, `gm_gauntlet.hpp`, `gm_applier.hpp`, `gm_rules.hpp`, or `CMakeLists.txt`, the same "GUI-layer only" shape as `docs/specs/woz-gui-qol.md`.

- `room_path` is already a `main()`-local computed once near the top of `main()` (`argc`/`argv` parsing) and stays in scope for the whole function, including the main loop — New Session's reload reuses it as-is, no new storage needed.
- The reload reuses the exact same `parse_world(slurp(room_path))` call the startup path already makes, and the button's click handler reuses the same `try { ... } catch (const std::exception&) { ... }` shape Submit's and Save's handlers already have — just assigning into a New-Session-local error variable instead of the WorkOrder panel's `parse_error`, per the reload-failure decision above. That new variable is a `std::optional<std::string>` alongside `parse_error` (same type, same red-text rendering idiom, different variable and different render site).
- `kGuiLogPath`'s single `constexpr const char*` becomes a per-session `std::string` (generated once at startup, regenerated on each New Session click), threaded into the same `process_turn(world, turn_number, wo, log_path)` call Submit's handler already makes — only the value changes, not the call shape.
- Reuses `gm_log.hpp`'s existing replay-check machinery unchanged (locked in `docs/specs/gm-adjudicator.md`) — each generated log file is independently replayable exactly like `gui_session_log.jsonl` is today, just under a new name.

## 5. Open Questions

None — the four scope forks raised during drafting (reset scope, log-file rotation, confirmation, room-file choice) are resolved above. A subsequent `/spec-review` pass, grounded against the actual current `woz_gui.cpp`/`.gitignore`/`gm_log.hpp`, surfaced three further gaps — the reset list omitting `wo_preview_text`/`parse_error`, the failure-path error's render location being ambiguous, and second-granularity timestamps not actually guaranteeing Goal 3's "ever" claim against a realistic double-click — all resolved and folded into §4 above. None remain open.
